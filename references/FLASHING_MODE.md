# Flashing Mode

The Hudiy application menu has a **Flashing Mode** action beside **Toggle
Diagnostics**. Its status icon is visible only when inhibition is on. State is
saved in `~/.hudiy/flashing_mode.json` and survives app/service restarts and
reboots. The icon also reflects automatic activation by the Haldex UI flasher.

The flasher enables this mode after obtaining acknowledged diagnostic ownership
and before opening its CAN device. It leaves the mode enabled after completion
or failure. Turn it off manually when finished; turning it off during an active
flash is rejected. An ECU recovery marker also blocks disabling it until the
bench recovery procedure has resolved the incomplete ECU state.

## Inhibited traffic

- Central gateway application TX: DIS top-display updates, base-function
  presence messages, Haldex mode bursts and other producers using `can_send.ipc`.
  The gateway consumes/discards inhibited frames rather than replaying them.
- DIS direct SocketCAN TX: session state and cached responses are cleared,
  and its socket closes when inhibition is observed.
- TP2 diagnostic and Openpilot direct TX: send guards reject traffic;
  the worker stops its receiver and closes polling sessions. User-enabled
  diagnostic preferences are retained.
- Haldex mode manager: bursts are skipped; desired mode is retained for resume.

The flasher uses its own SocketCAN adapter and remains permitted. Passive CAN
reception, capture/logging, Hudiy communication and control commands remain
available. This does not disable the physical bus or silence other vehicle ECUs.
It inhibits all application senders above, including on different configured CAN
interfaces. No essential wake-up frame exemption is currently configured.

## Ownership and persistence

Each actual background `bus.send` holds a common Linux `flock` until that call
returns. Enabling the mode takes that same lock, so its acknowledgement follows
all in-flight application send calls; subsequent calls are inhibited. Persistent
state is written by atomic replace with file and directory fsync. A separate
operation lock prevents toggling off during flashing and cleanup. Corrupt mode
state and an existing recovery marker fail closed.

`bus.send` completion is the adapter's queue-acceptance boundary, not proof that
the final frame physically left the CAN controller. Driver TX timing, gateway
reachability without application presence messages and service restart behavior
still require acceptance on the recoverable Linux bench before vehicle use.
Windows tests use process-local locks; production process exclusion uses Linux
flock. All participating services must run as the same configured installation
user so they share this state directory, as generated by `install.sh`.

## Offline checks and bench acceptance

Run `python -m unittest discover -s tests -v`. These tests use temporary state
directories, fake buses and isolated service definitions; they do not open CAN.
They exercise persisted state, an in-flight send race, disable protection,
automatic activation, retained inhibition, sender blocking and cleanup.

On the recoverable bench, install all changed services together. Confirm:

1. Toggle on: the icon appears and app-generated DIS, diagnostic and mode frames
   stop; passive capture continues. Toggle off: the icon disappears, DIS starts
   a fresh session and previously enabled services resume.
2. Restart Hudiy and each sender, then reboot the host while enabled: no app TX
   resumes and the icon reflects the saved mode. Test prior diagnostics disabled.
3. Start an installed-UI flash: mode turns on automatically; only the flasher's
   diagnostic channel transmits. A concurrent toggle-off is rejected.
4. After successful verification, the icon and inhibition remain on until the
   user toggles off. After destructive failure, recovery remains required and
   toggle-off is rejected. Perform failure/recovery tests on the bench only.
5. Check CAN controller timestamps and reachability with all app TX inhibited.
   If the specific topology requires a presence/wake-up frame, identify it from
   evidence and add a narrowly scoped exemption before accepting the deployment.

No physical CAN/J2534 testing was performed while implementing this feature.
