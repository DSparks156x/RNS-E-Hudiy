Native bitmap row grouping (opt-in)

Bitmap application-message limits are internal transport policy: 105 bytes
for white clusters, 42 bytes for red clusters. They do not change CAN frame
gaps, negotiated TP2 ACK budgets, claim handling or whole-frame backpressure.
The removed bitmap-message-size setting is no longer read by the driver or
text layout. Old saved keys have no effect.

The bounded opt-in bench profile is:
  "ddp_bitmap_rows_per_command": 8
Merge this key into the existing config; bitmap_rows_profile_example.json
contains only this key and is not a complete replacement configuration.
The default row count remains 1. Red clusters always use one-row commands.
Grouping with coalescing enabled is rejected, from config or the runtime flag.

The driver accepts only integer row counts 1..12; 13..22 are rejected.
Every native 55 record is bounded by the internal message limit, the encoded
length field and remaining bitmap height. Row count is clamped to capacity.
Widths not divisible by 8 retain one-row records so padding cannot become
pixels in the following row.

Native single-55 multi-row 2/4/8 static patterns have been visually verified.
The variable 7/9/9/12/11 profile at 105-byte application messages was visually
correct at 10fps. Its uncapped 16.8 ACK/s run tore and yielded only a few actual
LCD updates/s; transfer rate is not usable presentation FPS. Fixed rows 22
failed LCD correctness despite ACKs and remains excluded.

The mechanism behind the 22-row failure remains unproven: possible native
signed length/command-buffer restriction or long-command streaming across
TP2 CONT boundaries. The fixed white limit avoids configurable larger
application messages placing grouped records across the 105-byte boundary.

The explicit draw_raw_bitmap_batch IPC command is incompatible with multi-row
grouping: the service publishes a matching frame NACK and sends no graphics.
Row count 1 retains the existing batch path. Use normal draw_raw_bitmap/frame
IPC for grouping.

The installed service is dis_client/dis_service.py, with regression coverage
in tests/test_bitmap_message_budget.py and tests/test_bitmap_rows_per_command.py.
No native J2534 batching, RAM enqueue fast path or variable-row optimizer is
introduced by row grouping. Bench transport measurements do not imply the
same rate from ordinary production CAN adapters.
