Behavior and safeguards:
- Capability format20 ->52; format10/company03 ->7A; other format10 ->5A.
  Unknown format retains the prior known family. Unknown-first still completes
  control setup and stays PAUSED with its renderer disabled. This does not add
  generic5A rendering or expand the existing restricted7A renderer.
- All capability tails, including the car's twelve-byte09 record ending in
  30 39 00 32 00, remain ONE raw application record. No second message, geometry
  interpretation or dimensions are invented from that tail.
- Standalone five-byte30 is optional observed compatibility telemetry only
  during initial01/08/20 response roles. It never selects or advances setup.
  Role closes before33. Exact already-received reserved objects are retired;
  new30 at33/finalA3/runtime follows native unknown-request0B0130 handling.
  Metadata can differ with actual receive timing; control outcome does not rely
  on metadata. The four-outstanding-object bound remains explicit host policy.
- Valid initialmode2 is answered01 02 00 and closed as an unsupported initial
  renderer profile. Nativephase10 does not query08 or force mode1. Runtime mode
  handling remains separate. Mode1 repeats during discovery are handled as described below; mode changes
  after the first20 and resets close the interrupted transaction.
- Each20 captures its causal receive boundary and capability generation.
  Previously received21 cannot confirm it. New09 queues newsetup, never silently
  confirms an old generation. Invalidfresh21 retries fresh20, bounded to three
  host attempts/1000ms waits. These host times are not inferred native ticks.
- Errors, malformed status, reset/reopen, pending recovery and capability FIFO
  overflow cannot publishREADY. Queueoverflow handling now also closes safely
  in shared runtime reconfiguration instead of publishing an older generation.
- Initial setup does not publishREADY during the queue drain. Terminal guards
  run after setup, releaseACK and finalkeepalive. Screen claims remain the
  display service's responsibility; READY is not proof of display ownership.

Repeated mode requests during discovery:
- Every real00 is reserved by receive-object identity, changes mode/subtype at
  RECEIVE time, and gets its own01 reply in FIFO order on the same TP session.
  Only that exact received object is retired AFTER its01 transport ACK.
- Discovery phase advances at receive time. Early eligible09 after the latest00
  permits20 without another08. A newer00 requires fresh09; already received older
  records cannot overwrite the family selected by a newer record.
